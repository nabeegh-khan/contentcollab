# 2026-11-25 why the 150 req/s step failed on 25 Nov (issue #184): not the code of #177 and #179; most likely the laptop's network path; cause not proven
Checked 25 Nov 15:22 to 15:51 UTC on the live site https://contentcollab.app, cluster do-nyc3-contentcollab (the 14:56 run is from docs/evidence/2026-11-25-load-hpa.txt). No code or manifest was changed.
Target of every run: GET /health through the Gateway, as in the 21 Nov run.
Script: scripts/loadtest.mjs (unchanged, 60 s per step) unless a row says "probe". The probe is a 30-line Node script kept in the scratchpad, not in the repository: the same fetch call, the same 5 s timeout and open-loop timer, with client CPU and event-loop lag added. It is a different script from loadtest.mjs.
Images: ef5d56f (PR #179) until about 15:42 UTC, then 38ed5cb (PR #186, merged by another block at 15:40 UTC and rolled out during these checks).

## Question and answer
The 25 Nov run at 15:01 UTC served 42 of 150 req/s (71.75% errors); on 21 Nov the same step had 0.06% errors. Is the cause the code added since 21 Nov (#177 Operations reads, #179 Grafana embedding), the cluster, or the client path?
- Code: no sign of it. #177 and #179 touch the Operations page and Grafana, not /health, and the laptop passed at 150 req/s on ef5d56f (15:29, 15:31) and on 38ed5cb (15:48).
- Intermittent, not steady: the same laptop passed and failed on the same site (below), once back to back (0% at 15:31, 26.6% at 15:32).
- Cluster: a Job inside the cluster on the node without the Gateway served 150.0 of 150 req/s with 0 errors (1 of 4 in-cluster runs, a single sample). The other three in-cluster runs, with the generator on the Gateway's node, failed in part (4.32%, 92.29%, 5.08%) and are confounded by the generator sharing that node.
- Client path: the leading explanation by elimination, not shown directly. Node CPU was not read during the laptop runs and the Gateway pod has no CPU request, so a Gateway starved by something else on its node is not excluded; against it, the Gateway pod used at most 0.14 cores and the API pods little during the 15:22 run.
- Why 21 Nov was clean is not known: the laptop's network state that day was not recorded.

## What the Gateway shows when a node is saturated (found, not changed)
Live nginx -T of the Gateway pod: worker_processes auto (2 workers), worker_connections 1024; the pod has no requests or limits (QoS BestEffort); one replica; upstream blocks without keepalive and without max_fails or fail_timeout, so nginx's defaults apply (1 failure, 10 s) with two API endpoints: one premature close can take both out for 10 s ("no live upstreams", 502). This was seen only when the generator saturated the node, not from the internet in run 4 or in the passing laptop runs. Whether the failed laptop runs involved the same weakness is not shown (node CPU unread). Giving the Gateway pod a CPU request is an open design question, not decided here.

## Limits
- Single samples throughout; the argument is the contrast between runs of the same code, not a count.
- Kept raw: the CSVs, the in-cluster job logs and (in the scratchpad, not the repository) the Gateway logs of runs 2, 4 and the 15:48 laptop run. Not kept: the Gateway text of the 15:22 laptop run and of run 1 (counts as read), the Prometheus outputs, the probe outputs, the netsh and ping outputs and the kubectl DNS error. They are recorded here as read.
- Prometheus here has no throttling, Postgres, Redis or node CPU series; those layers were not read.
- The image changed from ef5d56f to 38ed5cb between runs 2 and 3.
- Why 21 Nov was clean is not established.

## Verdict
No code fault found and no steady cluster fault: the step passes from the laptop and from a pod off the Gateway's node, and fails intermittently from the laptop. The most likely cause is the laptop's network path on 25 Nov, by elimination; it is not proven, and a Gateway starved on its node is not excluded. For the report, the load figures can come from run 4 and the 15:48 laptop run, quoted as single passing samples next to the failed ones (15:01, 15:22, 15:32).
