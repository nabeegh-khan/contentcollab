# api

The JSON API: Node.js, Express, Socket.IO.

Planned layout, mirroring the Assignment 2 starter so everyone already knows it:

```
api/
  src/
    server.ts        app setup, middleware order, listen only when run directly
    routes/          one file per resource: auth, documents, versions, shares, comments, tags, search, export
    middleware/      validation, auth and role checks, request logging, error handler
    services/        the work behind a route: storage client (Spaces), realtime (Socket.IO), queue (BullMQ)
    db/              Prisma schema or SQL, migrations, one shared client
    types.ts         raw input types and validated types, kept apart
  tests/             Jest and Supertest, one file per resource, run serially against a reset test database
  Dockerfile
  package.json
```

Rules that apply here are in `docs/PRACTICES.md` (API-*, DB-*, SEC-*, TST-*).

## Practices that apply here

From [`docs/PRACTICES.md`](../docs/PRACTICES.md) (generated by `scripts/sync-practices.py`; edit the source, not this list). Paste this section into whatever tool you write code with.

| ID | Practice | Here |
|---|---|---|
| CON-1 | One container per responsibility | api, web, postgres, redis, worker are separate services |
| CON-2 | In the Dockerfile copy the package manifests and install before copying the code, so the dependency layer is cached | Every Dockerfile in the repo |
| CON-3 | Pin base image versions (`node:24`, `postgres:18`, `redis:8`) | Rebuilds produce the same environment |
| CON-4 | Healthchecks on every service; dependents start on `condition: service_healthy` | Compose locally; readiness and liveness probes in Kubernetes |
| CON-5 | `init.sql` runs only on an empty data directory; after that, schema changes are migrations | Versioned migrations from the first week |
| CON-6 | Rebuild after code changes (`up --build`); plain `up` reuses the old image | Written into the README's local setup |
| CON-7 | Services reach each other by service name; publish only the ports outside clients need | Postgres and Redis are never published; only the Ingress is public |
| SEC-1 | Secrets in environment or a secret store, never in code or images; commit only `.env.example` | `.env` is ignored; Kubernetes Secrets in the cluster |
| SEC-2 | Prefer file-mounted secrets to environment variables for passwords and keys, and grant each secret only to the service that needs it | Database password mounted into api and worker only; Spaces keys into api and worker; nothing into web |
| SEC-3 | The app connects as its own database role with only the grants it needs, never the superuser | `contentcollab` role owns one database |
| SEC-4 | Protect API routes with a token in the `Authorization` header; leave only `/health` public | JWT on every route except health and sign-in |
| SEC-5 | Force HTTPS | TLS at the Ingress with cert-manager |
| SEC-6 | Run as a non-root user; SSH with keys only | Dockerfiles set a non-root user; pods run with `runAsNonRoot` |
| SEC-7 | Escape stored text before rendering it as HTML | Comment bodies and filenames are rendered as text, never injected as HTML |
| SEC-8 | Restrict network paths: firewall, private network, no public database port | Postgres and Redis on ClusterIP Services only |
| SEC-9 | Share links carry a random token and an expiry, and the role check runs on every request, not only when the link is created | `shares` table, role middleware |
| DB-1 | Persist in a database, not in process memory | Nothing the user created lives only in a container |
| DB-2 | Block storage for the database, object storage for files served over HTTP; a managed database alone is not "persistent storage" in this course | Postgres on a PersistentVolumeClaim; uploads in Spaces |
| DB-3 | Volumes are not backups and not shared storage | Nightly `pg_dump` to Spaces; files never written to a pod's disk |
| DB-4 | Parameterized queries only | Every query |
| DB-5 | Order every list query explicitly | `ORDER BY id` or `created_at` on every list |
| DB-6 | Multi-step writes in one transaction; a page and its total read in one transaction | Creating a version and its metadata; list endpoints |
| DB-7 | Return the row as stored (`RETURNING`), not an echo of the request | Every create and update |
| DB-8 | A cache is a copy; the database is the source of truth, and a missing cache key is re-seeded, never read as zero | Redis holds socket state and counters only |
| DB-9 | Rules in the schema as well as the API: `NOT NULL`, `CHECK`, foreign keys, timestamp defaults | Roles constrained to three values; every row timestamped |
| DB-10 | Enforce relationship rules in the API with a clear error | A document's last Owner cannot be removed |
| DB-11 | Find-or-create lookups run one at a time, never fanned out in parallel | Inviting a user who may already exist |
| DB-12 | Delete persistent data only on purpose (`down -v`, volume delete) | Never against demo data |
| API-1 | REST resources, standard methods, stateless requests, JSON bodies, status codes that match the outcome | The endpoint table in `docs/API.md` |
| API-2 | One fixed JSON error shape; details to the log, a generic 500 to the client | `{ error, message }` or `{ error, messages }` |
| API-3 | Body, params and query are untrusted: parse, validate, then use; report every validation error at once; check in a fixed order (ID format, body, existence, business rule) | Validation middleware on every route |
| API-4 | Paginate every list with a default and a maximum, returning `total`, `limit`, `offset` | Documents, versions, comments, search results |
| API-5 | Keep slow work off the request path: uploads stream to object storage, imports and thumbnails run in a worker | An upload never sits in memory; a bulk import never blocks a request |
| API-6 | Limit what one request can do: body size cap, allowed content types, upload size cap, rate limit per user | A 2 GB upload or a flood of requests cannot take the API down |
| API-7 | Handle shutdown signals: stop accepting requests, finish in-flight ones, close the database pool | Rolling updates and autoscaling drop no requests |
| API-8 | Health endpoint that the platform checks; readiness separate from liveness | `/health` for liveness; readiness only once Postgres and Redis answer |
| API-9 | Idempotent writes where a retry is possible: an import skips a file whose checksum already exists | Bulk import, repeated uploads of the same file |
| API-10 | Document the API as a contract so slices can be built in parallel | `docs/API.md` before feature work starts |
| TST-1 | Export the app without starting the server; tests drive it on a free port against a reset test database, serially | Jest and Supertest with a Postgres service container in CI |
| TST-2 | Write tests beyond the samples; assert exact codes, messages and shapes | Every route has a test for the happy path and each error |
| TST-3 | Probe what the tests skip with a curl script and read the bodies | `scripts/smoke.sh` run before every demo |
| TST-4 | Verify persistence by restarting the stack | The restart test is a rehearsed demo step |
| TST-5 | Tests run in CI on every pull request; `main` is deployable | GitHub Actions |
| OBS-1 | Log each request with time, method, path and status | Structured JSON logs so Kubernetes can collect them |
| OBS-2 | Read the logs before changing code | `kubectl logs` first |
| DES-4 | Modules with one job each: routes, validation, services, data access, realtime, storage client | `src/` layout |
